## Overview

**Claude Agent SDK for Go** - Unofficial Go SDK for Claude Code CLI integration. Provides programmatic interaction through `Query()` (one-shot) and `Client` (streaming) APIs. Aims for 100% Python SDK parity with idiomatic Go (progress: docs/parity.md and docs/tracking/).

- **Module**: `github.com/severity1/claude-agent-sdk-go`
- **Package**: `claudecode`
- **Go Version**: 1.18+

## Architecture

```
.
├── client.go              # Client interface and WithClient/WithClientTransport context managers
├── query.go               # Query API (one-shot operations)
├── errors.go              # Structured error types
├── transport.go           # Transport interface abstraction
├── types.go               # Re-exports of all internal types and constants for external consumers
├── options.go             # Options types and functional options
├── options_bench_test.go  # Options performance benchmarks
├── internal/
│   ├── cli/               # CLI discovery and command building
│   ├── control/           # Bidirectional control protocol (hooks, permissions, MCP)
│   ├── parser/            # JSON message parsing with speculative parsing
│   ├── shared/            # Shared types (Message, ContentBlock interfaces)
│   └── subprocess/        # Subprocess management and protocol adapter
├── examples/              # Usage examples (numbered by complexity)
└── docs/
    ├── architecture/      # Detailed architecture documentation
    └── tracking/          # Python SDK parity tracking (PR replay tracker)
```

**Data Flow**:
1. `Query()`/`Client` -> `Transport` interface -> `subprocess.Transport` -> Claude CLI
2. CLI stdout -> `parser.Parser` -> `shared.Message` types -> User code
3. Control protocol: `control.Protocol` <-> CLI (hooks, permissions, MCP)

**Documentation**: See ARCHITECTURE.md and CONTRIBUTING.md for comprehensive details on design patterns, interfaces, data flow, and contribution guidelines.

<!-- AUTO-MANAGED: conventions -->
## Code Conventions

- **Idiomatic Go**: Use `gofmt` formatting, standard naming conventions
- **Interface-driven**: All message types implement `Message`, all content blocks implement `ContentBlock`
- **Error handling**: Use `fmt.Errorf` with `%w` verb for wrapping, include contextual information
- **Context-first**: All blocking functions accept `context.Context` as first parameter
- **JSON handling**: Custom `UnmarshalJSON` for union types, discriminate on `"type"` field
- **Cyclomatic complexity**: Keep functions under complexity 15 (measured by gocyclo); use `//nolint:gocyclo` on functions that legitimately exceed the threshold (large table-driven test functions, complex orchestration); extract helpers (e.g. `buildToolsListResult` from `routeMcpMethod`) to keep dispatch switches within budget rather than suppressing with nolint; higher complexity acceptable for table-driven tests, examples, orchestration code, method dispatch
- **Naming patterns**: Interfaces describe behavior, implementations use concrete names, options use `WithXxx()`, errors use `XxxError` suffix
- **No unnecessary exports**: Keep identifiers unexported unless needed by external consumers

## Detected Patterns

- **Transport interface**: Central abstraction for CLI communication; use `MockTransport` for tests
- **Process cleanup**: SIGTERM -> wait 5 seconds -> SIGKILL; `startProcessWaiter()` is the sole `cmd.Wait()` caller, started right after `Start()`, and closes `processDone` on exit; `terminateProcess()` never calls `cmd.Wait()`, it waits on `processDone` and no longer treats `stdoutDone` (stdout EOF) as process exit (a CLI that closes stdout but stays alive must still be signaled); child stdout and the stderr callback use `os.Pipe` via `newChildOutputPipe()` instead of `cmd.StdoutPipe/StderrPipe` because `cmd.Wait()` closes those readers and drops buffered output (Python reads stdout to EOF, reaps separately); the `childPipeEnds` write ends are closed in the parent after `Start()`; `handleStdout(protocol, childProcess{cmd, done})` closes `stdoutDone` at stdout EOF (`signalStdoutDone`) before waiting for exit, then `childProcess.exitError(ctx, lastErrorResult)` returns `*shared.ProcessError` (ExitCode from ProcessState) for a non-zero exit, nil for a clean exit or cancelled ctx (`handleStdout` drops it while `t.closing` is closed); after an error `ResultMessage` the message is `"Claude Code returned an error result: <errors or subtype>"` (Python #918; `trackErrorResult` resets on any other message except system `session_state_changed`); `SendMessage` returns `*shared.ConnectionError` once `processDone` is closed and `IsConnected()` is false after exit (`processExitedLocked`); `isProcessAlreadyFinishedError()` suppresses expected termination errors including Windows `"TerminateProcess: Access is denied"`; graceful shutdown (tracker rows 14a/30, PR #163): `teardownLocked` order is close protocol+adapter, `close(t.closing)`, `stdinWriter.Close()` (does not wait for a blocked write), `terminateProcess()`, then `t.cancel()`, close the stdout read end (the CLI is reaped, so nothing it wrote is still owed to a reader, and a descendant that inherited stdout would otherwise keep `handleStdout` blocked in its read; `TestCloseDoesNotWaitForDescendantHoldingOutput`, mock modes `close_orphan_stdout`/`orphan_stdout_and_stderr` re-exec the test binary as the descendant), wait wg at most `pipeDrainGrace` (500ms, for the stderr callback to drain its pipe), cleanup; `terminateProcess` never reads `t.ctx`: wait 5s on `processDone` (grace after stdin EOF), SIGTERM, wait 5s, Kill, wait 5s via `waitProcessDone(d)` (Windows SIGTERM fails, goes to Kill); `handleStdout` keeps draining while `t.closing` is closed (msgChan send, `sendStreamError`, control routing and the `exitError` result are dropped); `Connect` uses `exec.Command` and a `t.ctx` from `context.Background()`, so the connect ctx bounds only connect + Initialize (`net.Dialer.DialContext` semantics) and the client lives until `Disconnect`; `queryIterator.watchContext()` closes the iterator when its ctx ends
- **stdinWriter**: `internal/subprocess/stdin.go`; `writeMu` serializes writes (Python `_write_lock`); `EndInput` waits for an in-flight write, `Close` does not (pipe close runs on a goroutine); `t.stdin` is `*stdinWriter`, non-nil after `EndInput` (`isClosed()`); `SendMessage` writes outside `t.mu` (`openStdin` helper); control delegations use `connectedProtocol()` and call the protocol outside `t.mu`; `ProtocolAdapter.Write` does not hold `pa.mu` during the write
- **Stderr callback delivery**: `handleStderrCallback` never checks `ctx.Done()` inside its scan loop, so lines already read still reach `StderrCallback` after cancel (Python parity: its stderr reader never drops a read line); pinned by `TestStderrCallbackDeliversLinesAfterCancel`
- **Buffer protection**: 1MB limit to prevent memory exhaustion; `parser.NewWithSize(n)` allows configurable override; the stdout scanner buffer is limit+1 so a line of exactly the limit passes; `bufio.ErrTooLong` becomes `parser.NewBufferOverflowError(limit, err)`, a `*JSONDecodeError` with text "JSON message exceeded maximum buffer size of N bytes" (same text as the parser)
- **Environment variables**: Set `CLAUDE_CODE_ENTRYPOINT` to identify SDK to CLI
- **buildEnvironment order**: drops the inherited `CLAUDECODE` variable, then sets `CLAUDE_AGENT_SDK_VERSION=shared.SDKVersion` last so user env cannot override it; `internal/shared/version.go` holds `SDKVersion` ("0.8.0"), and root `Version = shared.SDKVersion`
- **Setting sources argv**: `SettingSources` is nil by default (no flag); `WithSettingSources()` with no args gives a non-nil empty slice and emits `--setting-sources=`; non-empty values emit one token `--setting-sources=<csv>`
- **Skills on initialize**: `InitializeRequest.Skills *[]string` set by `control.WithSkills`; `Transport.skillsProtocolOption` sends it only when the option value is `[]string`
- **Thinking config**: `ThinkingConfig` is a sealed interface (unexported `thinkingArgs()`; `shared.ThinkingArgs(cfg)` is the helper for `internal/cli`, nil gives nil). `ThinkingConfigAdaptive{Display}` emits `--thinking adaptive`, `ThinkingConfigEnabled{BudgetTokens, Display}` emits `--max-thinking-tokens N`, `ThinkingConfigDisabled` emits `--thinking disabled`. `ThinkingDisplay` (`summarized`, `omitted`) emits `--thinking-display <v>`, never for disabled and not when empty. `Options.Thinking` takes precedence over `MaxThinkingTokens`. `addThinkingFlags` emits `--max-thinking-tokens` only when `MaxThinkingTokens > 0`. `NewOptions` no longer sets 8000, so the CLI chooses. `DefaultMaxThinkingTokens` and `WithMaxThinkingTokens` are deprecated; the `MaxThinkingTokens` field is not marked deprecated because staticcheck SA1019 would flag internal reads
- **Resume session options**: `ResumeSessionAt` (string) emits `--resume-session-at=<v>` when non-empty; `ResumeDropsTurn` (pointer) emits `--resume-drops-turn=<v>` when non-nil; `validateWindowsArgs(goos, options)` in `client.go` covers `resume`, `resume_session_at` and `resume_drops_turn`
- **Table-driven tests**: Use for complex scenarios with multiple test cases
- **Functional options**: `WithXxx()` pattern for configuration
- **Benchmark tests**: Use `var sink any` to prevent dead code elimination, always call `b.ReportAllocs()` and `b.ResetTimer()`
- **tool_use_result metadata**: `UserMessage.ToolUseResult` carries rich edit info (filePath, structuredPatch, diffs); check with `HasToolUseResult()` before accessing via `GetToolUseResult()`
- **parent_tool_use_id placement**: parsed from top-level JSON data (not nested `message` object) for `UserMessage`, `AssistantMessage`, and `StreamEvent`; identifies messages produced inside a subagent (Agent/Task tool)
- **AssistantMessage error field**: `AssistantMessage.Error` is `*AssistantMessageError` parsed from top-level `data["error"]` (not nested `data["message"]["error"]`); CLI wire format is `{"type":"assistant","error":"rate_limit","message":{...}}`; use `HasError()` to check presence, `IsRateLimited()` for rate limit specifically; `AssistantMessageError` constants (all Python SDK parity): `rate_limit`, `billing_error`, `server_error`, `authentication_failed`, `invalid_request`, `unknown`
- **Unified streaming transport (Python SDK PR #468)**: `subprocess.New(cliPath, options, entrypoint)` is the single constructor; both `Query()` and `Client` route through streaming mode (`--input-format stream-json`) and run the initialize handshake unconditionally so the agents map can travel on the initialize control request instead of the deprecated `--agents` CLI flag. The prompt for `Query()` is written to stdin as a user-message JSON line (`{"type":"user","session_id":"","message":{"role":"user","content":...},"parent_tool_use_id":null}`) after `Connect()` returns. Wire-shape pins (no `omitempty`, key always emitted): `StreamMessage.SessionID` and `StreamMessage.ParentToolUseID` always emit `"session_id":""` and `"parent_tool_use_id":null` when unset; `InitializeRequest.Hooks` always emits `"hooks":null` when no hooks are registered (matches Python `"hooks": hooks_config if hooks_config else None`). `Transport.EndInput(ctx)` is declared on the public `Transport` interface (parity-review W2 fix; previously only on `subprocess.Transport`, discovered via inline-interface assertion in query.go); closes the stdin write side only (idempotent); invoked by `queryIterator.start()` immediately when no bidirectional channel is needed, or after the first `ResultMessage` when hooks/CanUseTool/SDK-MCP/file-checkpointing keep the control protocol alive. The needs-bidirectional decision lives in `needsBidirectionalStdin()` in `query.go`. The Go gate is deliberately wider than Python's (Python: `sdk_mcp_servers` OR `hooks`; Go: those + `CanUseTool` + `EnableFileCheckpointing`) as an idiomatic-Go divergence - Go has no preflight rejection for `Query(str)` + `CanUseTool`, and `EnableFileCheckpointing` legitimately requires the control protocol because `RewindFiles()` rides over it. `agentsToMap` stripping is intentionally stricter than Python (`if v is not None`): description/prompt always emit, empty Tools and empty Model are dropped - Go's zero-value-as-unset semantics can't round-trip Python's preserve-empty-list/string behavior until Phase 2 #19 (Python PR #684) lands nullable AgentDefinition fields.
- **InitializeRequest omitempty asymmetry**: `Hooks` field has no `omitempty` (always emits `"hooks":null` when no hooks registered, matching Python wire shape); `Agents` field has `omitempty` (key absent when nil or empty map). Rationale: hooks absence is meaningful to the CLI; agents absence simply means no programmatic agents were configured. `examples/15_programmatic_subagents` Example 4 demonstrates a large-payload (~260 KB, 20 agents) that would previously exceed OS ARG_MAX via `--agents` but now streams safely over the initialize control request.
- **Init error routing**: the control protocol is built before `handleStdout(protocol)` starts and passed in, so stdout handling never reads `t.connected`/`t.protocol` unlocked. `routeInitError(protocol, msg)` is a free function in `io.go`: it detects an error `ResultMessage` arriving before initialize completes (`protocol.IsInitialized()`, checked under the protocol lock) and calls `protocol.HandleControlInitErr()` to unblock `SendControlRequest()` via `initErrChan`. `setupControlProtocol()` additionally spawns a watcher goroutine that calls `HandleControlInitErr()` when the CLI exits before responding to initialize (`stdoutDone` closed by `handleStdout` at stdout EOF, before the process exit wait); the watcher captures channel/protocol pointers locally to avoid races on reconnect. `HandleControlInitErr()` reads `p.initialized` under lock and is a no-op after `Initialize()` succeeds, so the post-init watcher cannot poison `initErrChan` for later `SendControlRequest` calls (e.g. `SetModel`/`GetMcpStatus`).
- **Concurrent control dispatch**: `Protocol.HandleIncomingMessageAsync()` runs each incoming `control_request` on its own goroutine (responses and regular messages stay inline) so a slow `CanUseTool`/hook/MCP callback cannot stall `handleStdout()`; per-request ctx cancel funcs live in `Protocol.inflightRequests` keyed by `request_id`, and `Close()` cancels all without waiting; `writeControlResponse()` checks ctx before writing and is used by all four response writers (error, permission, hook, MCP) so cancelled handlers write nothing; `replyHandlerFailure()` sends an error `control_response` for handler errors and panics; an unsupported subtype now returns an error (error response, Python parity) instead of being silently ignored; mock mode `two_permission_requests` and `TestTransportSlowPermissionCallbackDoesNotBlockReader` cover it
- **Control protocol delegation**: `Interrupt()`, `SetModel()`, `SetPermissionMode()`, `RewindFiles()`, `GetMcpStatus()` guard with `t.connected` (error `"transport not connected"`) before delegating to `t.protocol`; nil protocol guard uses descriptive error `"internal error: transport connected but control protocol is nil"`. `Interrupt()` sends only the `{"subtype":"interrupt"}` control request (Python `Query.interrupt()` parity) and never signals the process (no SIGINT, no Windows-unsupported error), so the CLI stays alive after an interrupt (issue #147). A delegation still waiting for its response when `Close()` runs returns `control.ErrProtocolClosed` at once (`TestCloseFailsPendingInterrupt`, mock mode `ignore_interrupt`), and one still waiting when the CLI's stream ends with an error (non-zero exit, scanner error) returns that error at once (`Protocol.FailPendingRequests`, called from `handleStdout`). (No more `closeStdin` gate - every connection runs control protocol now.)
- **MCP config serialization**: `generateMcpConfigFile()` strips Go `Instance` field from SDK servers and propagates `AlwaysLoad` explicitly (not via struct json tags) when building CLI config
- **Resume argv safety (Python PR #1123)**: `addSessionFlags` emits `--resume=<value>` as ONE argv token (the CLI declares `--resume` with an optional value, so a two-token form lets a dash-leading value like `--version` parse as a flag); `prepareOptions()` also calls `validateWindowsArgValue(runtime.GOOS, "resume", value)` in `client.go`, which rejects cmd.exe metacharacters (`&|<>^%!"`, CR/LF) only when goos is `windowsOS`, so `Query`, `QueryWithTransport` and `Client.Connect` all validate
- **Windows batch CLI refusal (Python PR #1127, BatBadBut CVE-2024-27980)**: `cli.RejectWindowsBatchCLI(goos, path)` returns `*shared.ConnectionError` on Windows for any path with a `.bat`/`.cmd` component (`isWindowsBatchPath` is pure string logic, also splits on `:`, so `claude.cmd:stream` and `claude.cmd.` are caught); `subprocess.Transport.Connect()` calls it before the version probe spawns the CLI. `FindCLI` on Windows prefers a native `claude.exe` over an npm `claude.cmd` PATH hit and keeps the batch hit only as last resort so Connect reports the clear refusal; the Windows common-locations list is only `~/.local/bin/claude.exe`. `addExtraFlags` emits `--flag=value` when the value starts with `-` (P32 item a; audit vs CLI 2.1.286: only optional-value flags `--debug`/`--resume` are injectable)
- **Permission suggestions**: `ToolPermissionContext.Suggestions []PermissionUpdate` carries CLI-provided permission suggestions to `CanUseTool` callbacks; `PermissionUpdate.Type` is one of `addRules`, `replaceRules`, `removeRules`, `setMode`, `addDirectories`, `removeDirectories`

- **streamErrChan fan-in**: `ClientImpl.streamErrChan chan error` (buffered, size 1) receives errors from `QueryStream` goroutine; passed directly to `clientIterator` alongside transport `errChan` and `streamErrChan`; `Next()` selects on both so callers see all stream errors without spawning goroutines; `clientIterator` and `queryIterator` read the transport channels through `streamReader` (`stream_reader.go`): a closed `errChan`/`streamErrChan` is set to nil for the call and reading continues, so `Next` never returns `(nil, nil)`; the transport sends its terminal error after the last message, so `streamReader` delivers every buffered message before the error (an error read early is held as `pending`) and, when `msgChan` closes, still returns an error left in `errChan` before `ErrNoMoreMessages`; `ClientImpl.stream` is shared by successive `ReceiveResponse` iterators, so the exit error after a turn's `ResultMessage` surfaces on the next call (`clientIterator.markClosed`); `QueryStream` write errors go to `streamErrChan` (surfaced by `ReceiveResponse`), with a stderr log only when the buffered error is dropped
- **Client Done/Err (issue #144 follow-up)**: `Client.Done()` closes when the connected CLI process exits (on its own or through `Disconnect`) and `Client.Err()` says why, following `context.Context`: nil while running, `*ProcessError` for a non-zero exit (ExitCode -1 for a signal), `*ConnectionError` for a clean exit, `errClientNotConnected` before `Connect`/after `Disconnect` (Done is then closed). The Go analog of Python `receive_messages()` raising the `ProcessError`, which a `<-chan Message` cannot carry. `ClientImpl` type-asserts the unexported `processWatcher` interface (`Done`/`Err`), which `subprocess.Transport` implements on `processDone` (no second waiter); `Done` does not wait for stdout EOF. ## Best Practices

- **TDD approach**: Write failing tests first, implement to make them pass
- **Test file organization**: Test functions first, then mocks, then helpers
- **Helper functions**: Always call `t.Helper()` in test utilities
- **Thread safety**: All mocks must be thread-safe with proper mutex usage
- **Self-contained tests**: Each test file has its own helpers to avoid dependencies
- **Benchmark organization**: Use table-driven benchmarks with realistic scenarios, measure allocations with `b.ReportAllocs()`
- **t.Fatal() + return**: Always follow `t.Fatal()` with `return` in subtests to prevent staticcheck SA5011 nil pointer dereference warnings (staticcheck does not track that t.Fatal() stops execution)
- **Cross-platform mock CLI via TestMain**: use `TestMain` + `os.Args[0]` re-entrancy (not `.bat`/`.sh` fixtures) for packages that need a mock subprocess; dispatch on a package-scoped env var set with `t.Setenv`; never use Windows-only skips to work around fixture limitations - the TestMain pattern works identically on all platforms
